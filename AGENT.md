# LivePulse Engineering Instructions

This file is the persistent engineering context for the LivePulse project.

Read and follow this file before making architectural or implementation decisions.

Do not treat the requirements below as suggestions. They define the project's engineering principles, constraints, and documentation standards.

When requirements conflict, prefer:

1. Correctness
2. Data consistency
3. Explicit failure handling
4. Simplicity
5. Measurable performance
6. Feature velocity

LivePulse — Real-Time Classroom Infrastructure

You are helping me build a serious backend/system-design personal project called LivePulse.

1. Project Goal

Build a production-style real-time classroom infrastructure platform that demonstrates strong understanding of:

- WebSockets
- horizontal scaling
- concurrent writes
- race conditions
- Redis
- PostgreSQL
- distributed state
- reconnect/recovery
- ordering guarantees
- failure handling
- observability
- load testing
- backend architecture

This is a personal portfolio project intended to be discussed deeply in backend and system-design interviews.

The goal is not to maximize the number of technologies or features.

The goal is to build a relatively small system with genuinely difficult engineering problems and measurable behavior.

⸻

2. Core Product

LivePulse allows a teacher to conduct a live classroom session.

The initial system should support:

Live Quiz

Teacher:

- creates a live session
- starts a quiz
- publishes a question
- optionally defines the correct answer
- closes the question

Students:

- join the live session
- receive questions through WebSocket
- submit answers
- receive real-time results/leaderboard updates

The system must support the concept of:

first correct answer wins

when the question is configured for it.

Doubt Queue

Students can raise doubts during a session.

The system should support:

- FIFO ordering
- priority
- teacher viewing the queue
- teacher resolving a doubt
- real-time queue updates

Presence

Students should be able to see whether participants are currently connected.

The system should support:

- connect
- disconnect
- heartbeat
- reconnect
- stale connection detection

Reconnection

If a student’s WebSocket connection drops:

- they should be able to reconnect
- they should recover the current session state
- they should not lose persisted answers
- their application state should be reconstructed from server-side state

3. Technology Stack

Use the following stack unless there is a strong engineering reason to change it.

Backend

- TypeScript
- Node.js
- Fastify
- ws

Do NOT use Socket.IO initially.

The purpose of using ws is to understand the WebSocket layer rather than hiding it behind a higher-level abstraction.

Database

- PostgreSQL
- Prisma

PostgreSQL is the durable source of truth.

Redis

Use Redis for:

- WebSocket instance-to-instance communication
- Pub/Sub
- atomic operations
- ephemeral session state
- doubt queue
- short-lived presence information

Use Redis Streams only where reliable asynchronous event processing genuinely benefits the design.

Do not add Redis structures merely for complexity.

Validation

- Zod

Authentication

- JWT
- HTTP-only cookies

Keep authentication simple initially.

Infrastructure

- Docker
- Docker Compose
- Nginx

The local Docker environment should run multiple WebSocket server instances.

Observability

- Pino
- Prometheus
- Grafana

Testing

- Vitest
- integration tests
- k6 for load testing

CI

- GitHub Actions

4. Architecture

Initial architecture:

                    Client
                      |
                HTTP / WebSocket
                      |
                 Nginx
                /      \
               /        \
        WS Server 1    WS Server 2
               \        /
                \      /
                  Redis
                    |
               PostgreSQL

Multiple WebSocket servers are intentional.

A user connected to WS Server 1 must be able to receive an event generated by a user connected to WS Server 2.

Redis Pub/Sub will provide cross-instance event propagation.

PostgreSQL remains the durable source of truth.

Redis should NOT become the permanent source of truth for important business data.

⸻

5. Important Engineering Problems

The project must explicitly solve and document these problems.

Problem 1 — First Correct Answer Wins

Two students may submit the correct answer within milliseconds.

Never implement:

read winner
if no winner:
write winner

because this introduces a race condition.

Use an atomic mechanism such as:

SET key studentId NX

or an appropriate PostgreSQL uniqueness/transaction strategy.

Document:

- the race condition
- the naive implementation
- why it fails
- the chosen solution
- why the chosen solution works
- trade-offs

⸻

6. Problem 2 — Reconnection

WebSocket connection state is ephemeral.

Application state must not depend entirely on the memory of one WebSocket server.

When a client reconnects:

Client
|
| reconnect
↓
WS Server
|
↓
Redis / PostgreSQL
|
↓
Current session state
|
↓
Client state restored

Document the distinction between:

- connection state
- session state
- durable state

⸻

7. Problem 3 — Ordering

The doubt queue must have a clearly defined ordering contract.

Define exactly what “fair” means.

Possible ordering model:

priority DESC
created_at ASC
sequence_id ASC

If concurrent requests require a server-generated sequence number, make the generation atomic.

Do not claim FIFO merely because requests usually arrive in order.

Document the actual ordering guarantees.

⸻

8. Problem 4 — Horizontal Scaling

The system must work with multiple WebSocket instances.

Example:

Student A
|
WS-1
|
| Redis Pub/Sub
|
WS-2
|
Teacher

A teacher connected to WS-2 must receive relevant events generated through WS-1.

Document:

- why one WebSocket server is insufficient
- what happens when there are multiple instances
- why Redis Pub/Sub is used
- what Pub/Sub does NOT guarantee
- what happens if a subscriber is temporarily unavailable

⸻

9. Problem 5 — Failure Recovery

We must intentionally kill one WebSocket server during testing.

Example:

WS-1
↓
500 connected clients
WS-1 crashes
↓
Clients reconnect
↓
State reconstructed
↓
System continues operating

Measure and document:

- number of disconnected clients
- reconnect time
- state recovery success
- lost messages, if any
- lost application data
- system behavior during recovery

Do not claim zero message loss unless it has actually been tested and demonstrated.

⸻

10. Load Testing

The system must eventually be tested with:

- 100 connections

Measure at minimum:

- successful connections
- failed connections
- message throughput
- p50 latency

13. WebSocket Protocol

Define an explicit event protocol.

Example:

client → server
session.join
quiz.answer
doubt.create
presence.heartbeat
session.reconnect

Server → client:

session.joined
quiz.started
quiz.question
quiz.answer.accepted
quiz.leaderboard.updated
doubt.created
doubt.queue.updated
doubt.resolved
presence.updated
session.state
error

Every event should have a defined schema.

Use Zod for runtime validation.

Document:

- event name
- direction
- payload
- validation
- acknowledgement behavior
- error behavior
- idempotency requirements

Do not finalize the protocol until the underlying state transitions are understood.

⸻

14. Database Design

Start with a relational model containing only necessary entities.

Likely entities:

users
sessions
session_participants
quizzes
questions
answers
doubts

Do not prematurely normalize or create dozens of tables.

For every important index, document:

- query it supports
- expected access pattern
- why the index exists

Later, inspect actual query plans where useful.

⸻

15. Redis Design

Document every important Redis key.

Example:

session:{sessionId}:state
session:{sessionId}:presence
quiz:{quizId}:winner
session:{sessionId}:doubts

For each key document:

- data structure
- purpose
- TTL
- owner
- whether it can be reconstructed
- what happens if it disappears

This distinction is important:

Redis data that can be reconstructed is fundamentally different from durable business data.

17. Testing Philosophy

Tests should cover behavior, not just line coverage.

Important tests include:

- two simultaneous correct answers
- duplicate answer submission
- answer submitted after quiz closes
- reconnect during active quiz
- reconnect after answer submission
- duplicate reconnect
- multiple WS instances
- message propagation between instances
- concurrent doubt creation
- priority ordering
- duplicate doubt submission
- Redis unavailable
- PostgreSQL unavailable
- WebSocket server crash

Concurrency tests should intentionally create races rather than merely execute requests sequentially.

21. Working Rules

Before implementing a major feature:

1. Explain the problem.
2. Identify the state involved.
3. Identify concurrency/failure concerns.
4. Propose the simplest viable design.
5. Explain alternatives.
6. Implement it.
7. Test it.
8. Document the result.
9. Measure it where applicable.

Never fabricate test results, benchmark numbers, production behavior, or scalability claims.

If an assumption has not been tested, explicitly label it as an assumption.

Prefer simple systems with measurable guarantees over complicated systems with vague claims.

The project should evolve based on actual engineering problems discovered during implementation.
